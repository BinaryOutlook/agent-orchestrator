# Discovery 4: IDEs, editors and single-agent harnesses - switching model/provider/agent mid-task

Researched 2026-10-10/11. Scope: how products keep context when the "brain" underneath changes, and editor features that hand a task from one agent to another.
Method: official docs fetched live, vendor blog posts, and source files read directly from GitHub (raw files; no repos cloned, no code run). Everything fetched was treated as data.

Legend. Class: A = cross-agent handoff (same task continues on a different agent/harness with context carried), B = model/provider picker inside one harness, C = multiple agents side by side with no conversation handoff, D = none, U = unclear.
Verified: V = verified from official doc / source file / vendor post (URL or path given), I = inferred (reasoning stated), U = could not establish.

## Details

### Amp (deep dive)

Timeline (all VERIFIED on ampcode.com):
- 2025-06-27 `/news/better-faster-cheaper-summaries`: a different, cheaper model is used for compacting and "new thread with summary".
- 2025-10-23 `/news/handoff` "Handoff (No More Compaction)": compaction and the "New Thread With Summary" button were removed and replaced with Handoff.
- 2026-01-13 `/news/ask-to-handoff`: you can simply ask the agent "Handoff and build an admin panel for this"; "The agent starts a new thread with the relevant context and keeps working."
- 2026-05-06 `/news/neo` "Amp, Rebuilt" (+ 2026-05-27 `/news/drop-the-neo`): the rebuilt CLI is "compaction-first"; "Compaction now runs automatically when the context window is 90% full"; "So handoff is out. Compaction is in." and "Handoff is gone ... we don't think it warrants the complexity introduced by many small, connected threads." Replacement for the cross-thread use case: reference the old thread and Amp "will read them and extract the relevant information" (Ctrl+O -> `thread: new` inserts a reference to the previous thread).
- Conflict to note: `https://ampcode.com/docs/threads` (fetched 2026-10-11) still says 'ask the agent to "Handoff and ..." and it starts a fresh thread with the context that matters'. Either docs lag the CLI or handoff survives in orb/web threads. Treat handoff as "removed from the CLI, status elsewhere unclear".

Handoff mechanism (original post, VERIFIED):
- Who writes the text: Amp itself. The user states a goal for the next thread (`/handoff now implement this for teams as well`), then "Amp then analyzes the current thread and generates a prompt to start the new thread, along with a list of relevant files."
- What goes in: a generated prompt plus a relevant-files list; explicitly NOT a summary of the whole thread: "Instead of summarizing a thread, you're extracting from it what matters for your next task."
- User edit: yes. "The generated prompt will then appear as a draft in the new thread so you can still review and edit it before sending."
- New thread: yes, always (design goal: "focused threads"; compaction "encourages long, meandering threads, in which you ... stack summary on top of summary").
- Entry points: CLI `/handoff <goal>`, editor extension token-usage hover, later natural language ("Handoff and ...").

Model locking (VERIFIED, https://ampcode.com/docs/the-dial): "A thread keeps the mode you chose when you sent its first message. You cannot change the mode later in that thread." Two stated reasons: "most models get confused when they continue a conversation that another model started, and in our experience the results were never good" and each mode has its own system prompt and tool definitions, so switching "invalidates the prompt cache and makes the thread more expensive." To change brains you start a new thread (this is the philosophical opposite of replay-everything).

Oracle and friends (VERIFIED, https://ampcode.com/docs/models-and-subagents): Oracle is a specialist subagent for "difficult reasoning and planning questions", with Search, Librarian, Task and Read Thread. "Each subagent has its own context window", runs its own model chosen independently of the main agent, and "start[s] with the instructions and context the main agent gives them rather than the full conversation"; main agent only receives the final summary. So Amp mixes models by delegation, never by swapping the model of a live thread. Model Routing (docs/customize/model-routing) swaps which provider serves a model (API keys, ChatGPT subscription, Bedrock, OpenRouter etc.), a backend switch.

### VS Code + GitHub Copilot (deep dive)

Three distinct mechanisms, all VERIFIED:

1. Session Target handoff (new in the Agents docs, fetched 2026-10-11): VS Code supports Copilot, Anthropic Claude and OpenAI Codex harnesses plus a Cloud target. "When you change the target for an ongoing session, VS Code considers this a handoff and carries the conversation history and context to the new target." Handoff "can change the harness, execution environment, or agent role." Initiated only from a Local session. "The tools, permissions, and models might change because each harness ... provides different capabilities." Compared with Fork (independent session from a point in the conversation) and Switch surfaces (same session, different UI). Cloud target "can't access VS Code built-in tools or local development context." Copilot harness runs in an out-of-process Agent Host built on the GitHub Copilot SDK; Claude uses Anthropic's Claude Agent SDK; Codex via the OpenAI Codex extension or experimentally on Agent Host. The docs do not say how history is serialised for a different harness. Source hint: VS Code's agent host telemetry counts a `codexProviderSwitch` (OpenAI <-> Copilot model provider) "only after `turn/start` accepts a turn on the same thread" (`src/vs/platform/agentHost/AGENTS.md`), i.e. for Codex the provider can change on the same Codex thread.
2. Delegation to Copilot CLI / cloud agent ("Continue in", `@cloud`, `/delegate`): source shows the history is summarised by a model: `ChatDelegationSummaryService.summarize()` calls `ChatSummarizer.provideChatSummary(context)`; summaries over 100 chars are stored as a virtual document `copilot-delegated-chat-summary:` and attached as a prompt reference named "Delegation Summary" ("Summary of previous chat history for delegated request"); the visible prompt becomes "Complete the task as described in the [summary](...)"; summary state pruned after 7 days. (`extensions/copilot/src/extension/chatSessions/copilotcli/common/delegationSummaryService.ts`.) Cloud agent docs: when a session starts from a chat, "the session incorporates the context of your conversation" (no detail), branch + draft PR created; `/delegate` or `&` first asks to commit unstaged changes to a new branch.
3. Custom agent `handoffs:` frontmatter (https://code.visualstudio.com/docs/copilot/customization/custom-agents): fields `label`, `agent`, `prompt`, `send` (default false), `model` (e.g. `GPT-5 (copilot)`). Buttons appear after a response finishes. Source (`chatWidget.ts executeHandoff`): for a normal handoff it switches the agent/mode in the SAME chat (no new session), optionally requests the named model, writes the author-supplied static `prompt` into the input box (user can edit), and auto-submits only if `send: true`. If the user instead picks a "Continue in" destination from the chevron it sends `@<agentId> <prompt>` to that chat-session provider (background/cloud), which uses mechanism 2. So the handoff text is written by the agent-file author ahead of time (e.g. "Start Implementation"), not generated; context carried is simply the existing chat history ("conversation context"), since the session continues.

Other: Rubber Duck (built-in critic that "uses a complementary model" and returns blocking/non-blocking issues) and subagents ("context-isolated"); session history can sync to GitHub; Copilot CLI sessions can be discovered and continued in VS Code; "Resume in Terminal".

### Zed

- Docs: External agents run in their own process over ACP and "usually own" runtime, auth, model selection, tools; chosen "when you start a thread". No statement that a live thread can change agent. You can import existing threads from configured external agents into Thread History (imported threads archived until restored). Agent Panel doc lists "New From Summary" (fresh Zed Agent thread seeded with a summary), auto compaction (threshold, `/compact`, minimum 80k window) and says model switching is "clicking the model selector"; it says nothing about context effects of a model switch.
- Source (`crates/agent/src/thread.rs` @ main): messages are `User | Agent | Resume | Compaction`; `Thread::set_model` replaces the model, recomputes prompt capabilities and token usage, re-emits events, and propagates to subagents that `inherits_parent_model_settings`; it does not rewrite history. Agent content keeps `Thinking { text, signature }` and `RedactedThinking`. `CompactionInfo` is `Summary(text)` or `ProviderNative { provider, items }`. Provider-specific scrubbing is not in this file (INFERRED to be in each provider crate).

### OpenCode

Repo is now `anomalyco/opencode` (sst/opencode redirects). `dev` branch is a v2 monorepo (`packages/core`, `packages/ai`, `packages/schema`...). Source facts (VERIFIED):
- Per step, `SessionContext.load` re-resolves the session's model and reads history with `SessionProviderContext.provenance(model)` (`packages/core/src/session/context.ts`). So the model can change between steps and history is re-read, not stored per model.
- `provider-context.ts`: provenance = providerID + provider + modelID + route + protocol + sha256(endpoint). `compatible(source, target)` is a deep-equal. `history.ts`: "Local summaries always bound history. Native windows do for model-neutral readers, never for the original transcript, and only when the target model can replay them." I.e. a provider-native compaction checkpoint (e.g. OpenAI Responses compaction) is only used when the target model matches; otherwise the system falls back to the original transcript / local summary.
- `packages/ai/src/protocols/anthropic-messages.ts` ~L933-957: reasoning parts are sent as `thinking` only when they carry a valid Anthropic signature (`part.encrypted` or provider metadata); signature-less parts with `redactedData` go as `redacted_thinking`; otherwise empty ones are skipped and non-empty ones "demote[d] to text so the conversation remains sendable."
- `packages/core/src/session/affinity.ts`: sessions group provider cache routing by parent/fork source id.
- Docs (https://opencode.ai/docs/models/): `/models` to select; "variants" (reasoning levels) per model; `variant_cycle` keybind; no statement about history on switch.
- Kilo CLI is an OpenCode fork.

### Cursor

- Primary source (https://cursor.com/blog/continually-improving-agent-harness, 2026-04-30, section "Facilitating mid-chat model switching"): "When a user switches models, Cursor automatically switches to the appropriate harness, with that model's customized set of prompts and tools. However, the model still has to apply those tools to a conversation history that was produced by a different model and is out of distribution." Mitigation: "custom instructions that tell the model when it's taking over mid-chat from another model" which also "steer it away from calling tools that appear in the conversation history but aren't part of its own tool set." Cache: "caches are provider- and model-specific, so switching means a cache miss and a slower, more expensive first turn"; they "experimented" with summarising at switch time, but "the summary can lose important details." Recommendation: "stay with one model for the duration of a conversation"; alternative is a subagent with a chosen model and fresh context.
- Cursor staff (forum, 2026-07-28): in Auto mode the router picks a model per request, "the chat context is still passed along no matter which model answers", "the prefix cache is tied to a specific model".
- Cloud agents: docs say cloud agents "clone your repo ... work on a separate branch, then push changes to your repo for handoff" (https://cursor.com/docs/cloud-agent). Changelog 3.7 (cursor.com/changelog/cloud-in-agents-window) lists handoff between local and cloud ("Move to" machine/cloud) and CLI 2026-01-16 added `&` prefix to push a conversation to a cloud agent. Forum bug (3.6.31): cloud-origin agents lacked "Move to local"; fallback was fetching the branch and starting a new local agent, losing chat history. Transfer payload is NOT documented (INFERRED: transcript + git state).

### Claude Code (single-harness reference)

- `/model` mid-session (https://code.claude.com/docs/en/model-config); picker `Enter` = switch and save default, `s` = this session only. Docs do not discuss the transcript on switch (it is simply re-sent).
- Prompt-caching page (fetched 2026-10-11): "Each model has its own cache. Switching ... means the next request reads the entire conversation history with no cache hits." The CLI "asks you to confirm the switch only while the cache is still warm and the new model isn't the one that produced the last response"; `PreModelSwitch` hook can require or skip confirmation. `opusplan` toggles are model switches. Automatic model fallback (safety classifier) is also a model switch and "the session continues there". Skills with a `model:` frontmatter cause a one-turn switch. Subagent: "starts its own conversation with its own system prompt and tool set"; model inherits from session unless set in definition or `CLAUDE_CODE_SUBAGENT_MODEL`; fork subagents inherit history exactly.
- Resumed sessions keep their saved model.

### Codex CLI

Source (VERIFIED): `model_switch_instructions.rs` emits a developer-role fragment wrapped in `<model_switch>...</model_switch>` with the text quoted in the table; `session/mod.rs` doc comment: "If full context is injected and a model switch occurred, this prepends the `<model_switch>` developer message so model-specific instructions are not lost." Tests (`model_switching.rs`) cover: model change appends instructions, settings updates mid-turn apply to next turn only, media is projected "without changing live or replayed history" (live history keeps the image, projection is per request), switching to a smaller model updates the context window; compaction snapshots named `pre_sampling_model_switch_compaction` exist (INFERRED: compacts before sampling when the new window is smaller). Resume with a different model warns: "This session was recorded with model `X` but is resuming with `Y`. Consider switching back to `X` as it may affect Codex performance." Docs: `codex resume`, `codex fork` (forks transcript into new chat).

### Pi coding agent (cross-provider replay reference)

`transformMessages(messages, model, normalizeToolCallId)` (`packages/ai/src/api/transform-messages.ts`), VERIFIED:
1. Normalises null content, downgrades images to a text placeholder if target model lacks image input.
2. User/system messages pass unchanged. Assistant message is "same model" only if provider, api and model id all match.
3. Redacted thinking: kept only for same model, else dropped. Thinking with signature: kept for same model; else non-empty thinking text becomes a plain text block (README says `<thinking>` tags; the code at main emits untagged text), empty thinking dropped.
4. Text for foreign messages re-emitted as plain text. Tool calls keep content, lose `thoughtSignature`, and ids are normalised via a per-provider function (OpenAI Responses ids can be 450+ chars with `|`; Anthropic requires `^[a-zA-Z0-9_-]+$` max 64) with a map applied to the matching tool results.
5. Second pass inserts synthetic empty tool results for orphaned tool calls "to preserve thinking signatures and satisfy API requirements".
The README claims switching "mid-conversation while preserving context, including thinking blocks, tool calls, and tool results" and ships a `cross-provider-handoff.test.ts`.

### Aider

- `/model` -> `SwitchCoder(main_model=..., edit_format=...)` (commands.py L87-112) -> `Coder.create(from_coder=old)` copies `done_messages`, `cur_messages`, files, read-only files, cost, token counters. Only exception: when the edit format changes and `summarize_from_coder` is true, history goes through `summarizer.summarize_all` (if that fails: warn and keep full history). Code comment: old ASSISTANT messages in the old edit format "confused the new LLM. It may try and imitate it".
- Architect mode: after the architect's reply, `ArchitectCoder.reply_completed` creates an editor Coder with `done_messages = []`, `cur_messages = []`, cache disabled, `summarize_from_coder=False`, then runs it with the architect reply as the message: the architect's text IS the handoff. After success the architect side records "I made those changes to the files."

- Crush: see table; `Message` has `Provider`, `Model` fields and `ReasoningContent` carries three providers' replay artefacts, which is the "store everything, filter at lowering time" pattern. Auto-summarise when remaining context below threshold.
- Gemini CLI: `/model manage|set`, `/compress`, `/chat save|resume|share`, `/clear`. Replaced by Antigravity CLI for unpaid/Google One users (2026-06-18) per docs banner.
- Antigravity: model choice persists across messages; mid-run changes take effect next turn.
- Warp: model selector per conversation; Agent Profiles set base model; unavailable model -> automatic fallback chain; third-party CLI agents are enhanced (rich input, notifications, code review) but not switched between.
- JetBrains: the AI chat's agent selector (Junie, Claude Agent, Codex, any ACP registry agent) is the only "multi-agent in one chat" surface found; shared-history behaviour is undocumented in what I retrieved.

### LLM gateways / routers (one paragraph, as requested)

claude-code-router (musistudio, ~37.6k stars; "route across models" for Claude Code), LiteLLM (BerriAI, 60.9k; OpenAI-format proxy to 100+ providers), OpenRouter presets/fallbacks, CCS (kaitranntt/ccs; switches Claude accounts, Gemini, Copilot, OpenRouter via a local proxy) and cc-switch (farion1231, 142k stars; desktop switcher for Claude Code, Codex, OpenCode, OpenClaw configs) all work at the API/config layer: the harness keeps its own transcript and tool schema and simply sees a different base URL/model. Consequently they do not hand off a conversation; the harness replays its history to whatever model answers, and any provider-specific parts (Anthropic thinking signatures, OpenAI encrypted reasoning, tool-id formats, `cache_control`) are the gateway's problem. Claude Code's own docs warn that with a custom `ANTHROPIC_BASE_URL` or gateway "what stays cached depends on how the gateway handles the cache_control markers." (Repo metadata checked via GitHub API 2026-10-10; behaviour of each gateway not individually verified.)

## Patterns

1. **Harness-owned neutral transcript, replay on switch** (switch = just change the model argument; whole history re-sent): Claude Code, Codex CLI, Cursor, Zed native, OpenCode, Crush, Pi, Aider, Goose, Cline, Kilo, Antigravity, Kiro, Augment (inferred for Gemini CLI, Continue, Trae, Warp).
2. **Lowering/sanitising provider-specific parts at request time** (keep full fidelity in storage, convert when sending): Pi (thinking -> text, drop redacted thinking, strip thought signatures, normalise tool ids, placeholder images, synthetic tool results), OpenCode (unsigned reasoning -> text, signature/redacted round-trip only for Anthropic), Codex (media projection per model), Crush (stores Anthropic/Google/OpenAI artefacts side by side).
3. **Inject a "you are taking over" note for the new brain**: Cursor custom instructions + steering away from foreign tools; Codex `<model_switch>` developer message carrying the new model's own instructions.
4. **Swap the whole harness config (prompt + tool set) with the model**: Cursor ("switches to the appropriate harness"), Codex (new model instructions), Claude Code skills/opusplan.
5. **Summarise or compact before/at the switch**: Aider (when edit format changes), Cursor (experimental summary at switch to soften cache miss), Gemini CLI `/compress`, Zed compaction and "New From Summary", Amp Neo auto-compaction at 90%, Claude Code `/compact`.
6. **Native-provider checkpoint only if target matches, else fall back to portable summary/transcript**: OpenCode provenance check; Zed `CompactionInfo::ProviderNative{provider}` vs `Summary`.
7. **New thread seeded with a generated handoff prompt (+ file list), user-editable**: Amp Handoff (removed 2026-05), Cline `/newtask`, VS Code/Copilot delegation (summary doc as reference), Zed New From Summary.
8. **Same session, switch agent role/model with an author-written canned prompt**: VS Code custom-agent `handoffs:` (label/agent/prompt/send/model), Roo/Kilo mode switching (Cline Plan/Act with per-mode model).
9. **Cross-harness handoff inside one host app, history carried by host**: VS Code Session Target (Copilot <-> Claude <-> Codex <-> Cloud), Cursor local <-> cloud "Move to". Payload format undocumented.
10. **Delegation with context isolation (fresh window, brief in, summary out)**: Amp subagents (Oracle/Librarian/Task/Read Thread), Roo Boomerang, Claude Code subagents (model pin per subagent), Cursor subagent with chosen model, Goose subagents, VS Code subagents, Aider architect -> editor (empty history, architect reply as brief).
11. **Lock the brain per thread; to change, start a new thread**: Amp Dial (first message fixes mode). Reason given: other-model histories confuse models, and prompts/tools/cache differ per mode.
12. **Git/PR as the handoff medium**: Cursor cloud agents, Copilot cloud agent (`/delegate` checkpoint commit, draft PR), Augment Remote Agent (own branch). Chat history does not travel in the fallback path (Cursor forum bug).
13. **Link back to prior thread instead of copying**: Amp thread references (`@T-...`, read-thread subagent) and `Amp-Thread-ID` git trailer; Zed imported threads kept archived with restore.
14. **Cache-awareness and switch friction**: Claude Code confirm prompt while cache is warm + `PreModelSwitch` hook; Cursor "stay with one model"; Amp locks modes for cache reasons; Antigravity/Codex apply mid-turn changes only from the next turn.
15. **Resume-with-different-model warning**: Codex ("may affect Codex performance"), Claude Code resumed sessions keep their saved model.
16. **Backend-only switch (gateway)**: claude-code-router, LiteLLM, OpenRouter, CCS, cc-switch, Amp Model Routing.
17. **Shared-protocol multi-agent host with per-agent threads**: Zed ACP and JetBrains ACP registry (agent owns session/model; host owns UI/thread list). No cross-agent context.

## Ideas worth stealing (for AO provider switching)

1. **Handoff text written by the departing agent, aimed at a goal, shown as an editable draft** (Amp): ask user for next-task goal, have source agent produce prompt + relevant-file list, drop it into the new agent's composer unsent. Avoids the "lossy blob" criticism of compaction and gives user a final review.
2. **Attach the summary as a referenced artefact, not inline prose** (VS Code `Delegation Summary` virtual doc with prompt "Complete the task as described in the summary"): keeps the visible prompt short, summary inspectable and re-readable, expires after 7 days.
3. **Keep an AO-owned, provider-neutral transcript with per-part provider metadata namespaced by provider/model; sanitise at send time** (Pi/OpenCode/Crush): same-model turns replay verbatim, cross-model turns get thinking -> text, drop encrypted/redacted reasoning, strip thought signatures, normalise tool-call ids, placeholder unsupported media, close orphan tool calls with synthetic results.
4. **Tell the incoming agent it is taking over** (Cursor, Codex `<model_switch>`): one short system/developer note: previous agent name, that earlier tool calls may reference tools it lacks, instructions for its own tool set.
5. **Offer two switch tiers**: "continue same thread (replay + sanitise)" for B-type model changes vs "new thread with generated handoff" for harness changes (Claude Code -> Codex), mirroring VS Code's Fork vs Handoff vs Switch surfaces. Show which things will change (tools, permissions, models) as VS Code does.
6. **Treat native session state as non-portable**: Claude `session id`/JSONL, Codex rollout, encrypted reasoning, native compaction windows should only be reused if provenance (provider, model, protocol, endpoint) matches, else fall back to the portable transcript (OpenCode provenance hash).
7. **Cache/cost warning at switch time and apply from the next turn**: Claude Code's "confirm while cache is warm" and Codex/Antigravity "next turn only"; AO can warn "first turn on the new agent re-reads everything".
8. **Idle-only switching with a canned handoff for plan -> implement** (VS Code custom-agent `handoffs:` with `send: false` default): useful for a "Plan with Claude, implement with Codex" one-click preset where the prompt is author-written and editable.
9. **Link back, don't copy**: store `handoff_from_session_id` and expose "read previous thread" to the new agent (Amp thread references / `Amp-Thread-ID` trailer / Zed archived imports); with git worktree shared, the filesystem diff is the strongest context carrier (Cursor and Copilot fall back to branch handoff).
10. **Context isolation for helper work instead of switching** (Cursor's own advice, Amp Oracle, Roo): when the user only wants a second opinion from another provider, spawn a fresh-context sub-session with a brief and return only a summary; reserve full handoff for taking over the task.
11. **Warn on resume with a different agent** (Codex): "This session was recorded with X, resuming with Y may affect performance."
12. **Cautionary tale**: Amp built handoff (Oct 2025) and removed it (May 2026) because auto-compaction by frontier models made "many small, connected threads" unnecessary, while Amp also says other-model histories "confuse" models. For AO, where the handoff crosses vendors (and compaction cannot be used because the target is a different CLI), a generated brief remains the only safe carrier; do not assume model-agnostic replay is enough for tool-heavy transcripts.
