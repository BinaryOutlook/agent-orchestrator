# Provider switching research: canonical coding-agent clients

Research snapshot: 2026-10-10 (client date, Asia/Kolkata). This is supporting research for AO's broader competitor analysis. Public documentation and source were inspected; these products were not installed or exercised with paid accounts. Links to `main`/`dev` are moving references, so version-sensitive findings are identified explicitly.

## Classification

- **Backend switching:** the product keeps its own agent loop and conversation, and changes the LLM/provider used for future requests. Claude and OpenAI models can share this conversation without spawning Claude Code or Codex CLI.
- **Harness handoff:** the product replaces an actual agent implementation, such as Claude Code with Codex, while retaining one outer work session. This requires an explicit context bridge or native-history translation; access to several agents alone does not establish it.
- **Model-only switching:** moving between models in one provider's family does not establish cross-provider support.
- **Confirmed** means an explicit primary-source claim or implementation supports the stated behavior. **Partial** means the product has a picker/integration but the required continuity remains unverified. **No evidence** means this research does not establish the requested feature, not proof that it can never exist.

## Architecture traces worth studying

### Pi: keep raw history, derive model context

Pi persists a session as a JSONL tree. Model changes are entries containing provider/model identity. Compaction has its own entry with `summary`, `firstKeptEntryId`, and `tokensBefore`; optional fields include a system/tool checkpoint, usage, details, and provenance. Rebuilding context selects the latest compaction on the active path, substitutes its summary for the covered prefix, and includes retained entries. The raw transcript is not replaced by that model-visible projection. [Session format](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md).

The compaction implementation uses a token-based recent-history budget (documented default: 20,000), not five user exchanges. Repeated compaction feeds the previous summary into the next summarization pass, and cut rules keep tool results paired with calls. [Compaction internals](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md).

Its cross-provider API layer converts foreign assistant thinking blocks to tagged text while preserving regular text and tool calls/results; same-provider/API assistant material can remain native. This is compatibility normalization inside one harness, not migration of another CLI's private session file. [AI package handoff documentation](https://github.com/earendil-works/pi/blob/main/packages/ai/README.md).

**AO inference:** use an explicit semantic checkpoint type with a coverage boundary and provenance. A generic activity display summary is not an interchangeable substitute. Keep complete UI history independently from bootstrap selection. AO can choose five completed user/final-assistant exchanges instead of Pi's richer token window; that is a deliberate reduction in detail.

### Aider: incompatible behavior can require summary conversion

`cmd_model` builds the new model, performs model sanity checks, adopts the new model's default edit format when the user was using the old default, then raises `SwitchCoder`. [`commands.py`](https://github.com/Aider-AI/aider/blob/main/aider/commands.py).

`Coder.create(from_coder=...)` brings along filenames, read-only files, current/done messages, commit hashes, totals and command state. If the edit format changes, it can summarize old completed messages: source comments explain that old assistant edit syntax can otherwise teach the new model to copy the wrong format. If summarization fails, it retains history and warns; old cache warming is disabled. [`base_coder.py`](https://github.com/Aider-AI/aider/blob/main/aider/coders/base_coder.py).

**AO inference:** a concise textual checkpoint is a sensible harness boundary. Do not replay foreign executable tool directives as though they were the target harness's own live calls. Preserve decisions, paths, current work, and final outcomes; let the target use its own tools.

### Goose: the protocol boundary is a real capability boundary

Goose documents `/model --provider` for same-session provider changes, and stores sessions in SQLite (`sessions.db`) from version 1.10.0 onward. Legacy JSONL files are imported and then left unmanaged. [CLI documentation](https://goose-docs.ai/docs/guides/goose-cli-commands/).

The current CLI `handle_model` refuses ACP targets and any source/target that manages its own context. For accepted providers it resolves the target before changing state, warns when the target context window is smaller, calls `switch_provider`, then refreshes the completion catalog. The refusal is explicit, not a missing button. [`session/mod.rs`](https://github.com/block/goose/blob/main/crates/goose-cli/src/session/mod.rs).

Separately, Goose can act as an ACP client for real Claude Code, Codex, Copilot, Gemini, Amp and Pi. The integration article also notes differences in mode/model support and MCP handling across agents. [ACP architecture article](https://goose-docs.ai/blog/2026/04/08/how-to-break-up-with-your-agent/).

**AO inference:** declare capabilities per adapter and interface: history capture, semantic checkpoint, fresh bootstrap, native resume, model list, and idle confirmation. Do not equate a process launcher/ACP integration with context-portable handoff. After changing ownership, refresh all provider-owned catalogs; the model selector is part of switch correctness.

### Roo Code: sticky profile and explicit switch are compatible

`activateProviderProfile` loads a profile, updates provider settings, rebuilds the current task's API handler, persists the task's profile selection, updates the webview, and emits `ProviderProfileChanged`. `getTaskWithId` separately loads API history from the existing task directory, alongside the UI-messages path. [`ClineProvider.ts`](https://github.com/RooCodeInc/Roo-Code/blob/main/src/core/webview/ClineProvider.ts).

The profile docs describe task-specific persistence to avoid another workspace/global selection unexpectedly changing an existing task. That does not prohibit a deliberate change in that task's chat dropdown. [Configuration profile docs](https://github.com/RooCodeInc/Roo-Code-Docs/blob/main/docs/features/api-configuration-profiles.mdx).

**AO inference:** persist the newly selected provider/model on the AO session; changing a global default should not silently rewrite existing sessions. Restore from durable session ownership after restart. Roo's shutdown makes this a code reference, not a current product recommendation.

### OpenCode: request state is distinct from durable conversation

The public V2 model endpoint changes the model for subsequent provider turns, and the picker updates the session without rewriting project defaults. [Model endpoint](https://dev.opencode.ai/v2/docs/api/session/v2-session-switchmodel/), [model selection](https://dev.opencode.ai/v2/docs/models/).

The current V2 session contract says execution reloads durable history and resolves selected agent/model before steps. Automatic compaction estimates the complete request against the selected model's window and output reserve, keeps full durable transcript, and renders summary plus retained recent context. Provider-native continuation state does not survive that compaction boundary. Startup recovery and ambiguous tool-side effects remain separate concerns. This is a moving `dev` contract, not proof every release ships it. [V2 session contract](https://github.com/anomalyco/opencode/blob/dev/specs/v2/session.md).

**AO inference:** an AO session is the durable user-visible work identity; provider-native continuation is disposable execution state. Switching cannot promise transfer of remote prompt caches. Make the bootstrap bounded and deterministic while acknowledging that the target may incur a fresh request prefix.

## Ideas to carry into AO's final recommendation

These are research-derived suggestions, not implemented changes:

1. Store three separate facts: immutable conversation history, semantic compaction checkpoints, and provider-switch events. Give each checkpoint a coverage boundary so overlapping recent messages are identifiable.
2. Handoff from the latest verified checkpoint plus the newest five **completed exchanges**, with only the user prompt and assistant final answer. Name the unit explicitly; five messages and five exchanges are different budgets.
3. Preserve the 32,000-character hard ceiling independently of the message count. Metadata, delimiters and clipping notices consume budget too. Prefer complete newest exchanges, then allocate the remainder to the checkpoint; if a single exchange exceeds the whole allowance, deterministic clipping is unavoidable and must be visible.
4. Maintain full timeline continuity even when the target receives a small context projection. Mark provider boundaries and checkpoint origin; do not change storage ownership when the displayed agent changes.
5. Scope every provider-owned selector/catalog by session provider or ownership generation, or evict/refetch on switch. Include models, effort, config options, skills, tools and permissions that actually differ.
6. Capture a compact deterministic workspace fact set: working directory/worktree, branch, changed paths, task intent, approval policy and pending work. Prefer file/path references over bulk source dumps.
7. Keep an adapter capability matrix; surface unsupported summary/native-resume behavior honestly. A short UI event label such as “compacted history” is not the generated semantic summary.
8. Keep idle-only handoff for AO's initial scope. Products that swap API models at a provider-turn boundary do not eliminate AO's separate process ownership/draining problem.
9. Provide a handoff inspector showing included checkpoint, exchanges, omitted count and final character total. This makes context quality reviewable without adding another summarization call.
10. Test switch-back as a context freshness problem. Resuming an old provider-native thread requires adding intervening work; creating a fresh target thread is simpler and avoids silently losing the other provider's turns.

## Unresolved limits

No arbitrary product's private cache or native provider thread was inspected. Closed-source model selectors establish user-facing selection, not their exact normalization or replay code. Current docs sometimes describe development contracts or redirect after rebranding. The strongest native-harness claim in this lane was deliberately rejected after the Goose source revealed an ACP switch restriction. Paid/account-gated validation was skipped as authorized; it is not marked as tested.
